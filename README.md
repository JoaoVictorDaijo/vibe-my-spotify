# Vibe My Spotify

Agentic curation for your own Spotify library, run from Claude Code. What
started as "dedupe my playlists" grew into a system that **learns your
taste**: AI judges propose, you rule, and every ruling becomes durable
doctrine the next cycle reads before judging. Edits land on your real
account through a vendored [spotify-mcp](spotify-mcp/) server and a
journaled, evidence-checked apply pipeline.

## What it does

### The placement pipeline
One question drives everything: *where does this song belong?* The
owner-approved pipeline is codified as a repo skill
([.claude/skills/track-placement](.claude/skills/track-placement/SKILL.md)):

1. **Ground mechanically first** — locate the track everywhere (playlists,
   Liked, exports), pull URI/ISRC/duration evidence. Zero LLM tokens.
2. **Read the vibes** — per-playlist profiles carry the accumulated rulings;
   judgment never re-derives a settled border.
3. **Judge by the band graph** — playlists are scene-bubbles, not
   surface-feature buckets; membership splits album-aware within a band,
   and sound-lineage overrides for sound-defined playlists.
4. **Escalate by stakes** — single delegated calls are decided inline; bulk
   or contested decisions go to two independent judge agents with identical
   mandates, a conciliator synthesizes convergence, and disagreements come
   back as owner toggles. The owner always has final say.
5. **Apply safely** — see the machinery below.

### The knowledge base (the taste-learning loop)
All state lives in a local, gitignored `curation-review/` folder:

- **Vibe profiles** — one file per playlist: theme, canon anchors, borders
  with sister playlists, every owner ruling with the tracks it touched,
  expulsions, watch items. Judgment jobs read these first.
- **Durable baseline** — the last known full export of every playlist +
  Liked Songs. A diff tool ([scripts/diff_baseline.py](scripts/diff_baseline.py))
  detects the owner's hand-edits between sessions — those are treated as
  taste signals and folded back into the vibes each cycle.
- **Verdict & proposal archives** — raw judge outputs and converged
  proposals are kept, so every decision has a traceable record.

The goal: each cycle the system gets measurably better at knowing what is
canonical for each playlist — good enough to advise, eventually to suggest.

### The apply machinery (irreversible writes, done carefully)
- Plans are generated by **evidence-checking scripts that refuse to emit**
  on any failed check: unique source match, keeper-verified live,
  destination free of URI / fuzzy-title / **ISRC** twins.
- [scripts/apply_plan_runner.py](scripts/apply_plan_runner.py) executes
  them: two-record journal, **adds strictly before removals**, hard
  verification gate before any deletion, drift = halt, canary on first
  write, resumable after interruption, full-content verification at the
  end. 100+ tests including fault injection.
- Every account write requires an explicitly owner-approved plan.

### The ghost fixer
Spotify silently delists album editions; your likes and playlist rows keep
pointing at the old URIs ("ghosts") — the UI stops showing hearts, you
re-add songs, edition dups breed. The toolkit:

- **ISRC trust audit** (local, zero API): finds every double-liked
  recording and every playlist↔Liked edition mismatch from exports alone.
- **Artist-page batch resolver**: one paged album listing + a few
  tracklist calls audit an artist's entire library presence (~10 rows per
  API call) — and the same responses contain each ghost's replacement URI.
- **URI remap registry** (`uri-remaps.json`): every discovered
  ghost→canonical mapping is stored permanently with evidence, status and
  fix locations — Liked-side and playlist-side repairs share one memory,
  and nothing is ever discovered twice.
- **Doctrines**: the curated roster is the edition authority; unplayable
  tracks are tombstones (never deleted — they may return); re-like date
  resets are protected by an archived, dated Liked snapshot.

### Token & API economy
- Mechanical work is plain scripts — never a model. Models only judge.
- Judgment reads compact `pos | artist – title` exports, not raw API JSON.
- The Feb-2026 API reality (dead /search, dead batch GETs, daily quotas,
  429 discipline) is mapped in [docs/spotify-rate-limits.md](docs/spotify-rate-limits.md)
  and survived by probe-first habits; recording identity falls back to
  MusicBrainz. Alternatives landscape:
  [docs/streaming-api-alternatives.md](docs/streaming-api-alternatives.md).
- Hard-won multi-agent process lessons:
  [docs/operation-learnings.md](docs/operation-learnings.md).

## Requirements

- Spotify **Premium** (required for Spotify dev-mode apps since Feb 2026)
- A Spotify app from the [developer dashboard](https://developer.spotify.com/dashboard) — Web API only, redirect URI `http://127.0.0.1:8080/callback`
- [uv](https://docs.astral.sh/uv/), Claude Code

## Setup

1. Create `.env` in the project root:

   ```
   CLIENT_ID=your_spotify_client_id
   CLIENT_SECRET=your_spotify_client_secret
   ```

2. One-time OAuth (opens your browser, or prints the URL to visit):

   ```
   ./auth.sh
   ```

3. Open the project in Claude Code and approve the `spotify` MCP server when prompted ([.mcp.json](.mcp.json) registers it; [run-server.sh](run-server.sh) launches it).
